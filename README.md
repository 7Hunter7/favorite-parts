# Favorit-Parts — поиск автозапчастей и аналогов

Двухэтапный поиск через API «Проценка».

## Стек

React 18, Redux Toolkit, Bootstrap 5.

## Запуск

```bash
npm install
npm start                    # http://localhost:3000
npm run build                # Сборка
```

## Переменные окружения

| Переменная              | Назначение      | Значение по умолчанию                      |
| ----------------------- | --------------- | ------------------------------------------ |
| `REACT_APP_FAVORIT_URL` | Базовый URL API | `https://api.favorit-parts.ru/hs/hsprice/` |
| `REACT_APP_FAVORIT_KEY` | Ключ покупателя | `00000000-0000-0000-0000-000000000001`     |

## Как работает

1. **Этап 1** — ввод артикула (дебаунс 700 мс, минимум 2 символа, только `A-Za-z0-9-/`) --> `GET ?key&number` --> уникальные бренды.
2. **Этап 2** — клик по бренду --> `GET ?key&number&brand&analogues=on&info=on` --> нормализованный список предложений.
3. **Цена** берётся **только из `warehouses[].price`** — поле `price` корня устарело (из документации).

## Ловушки API, которые обработаны

| Ловушка                                         | Обработка                               |
| ----------------------------------------------- | --------------------------------------- |
| `{error: "..."}`                                | показываем текст API в `ErrorBox`       |
| `goods: []`                                     | «производители не найдены»              |
| «Пустышка» (`brand:""`, `warehouses:[]`)        | отфильтровывается в `favoritApi`        |
| `analogues[]` только при `brand + analogues=on` | fallback на корневой товар              |
| `notRefund` только при `info=on`                | передаём `info=on`, рендерим бейдж      |
| Гонки запросов                                  | `requestId`-гард в `searchSlice`        |
| Падение рендера                                 | `ErrorBoundary`                         |
| Длинные наименования                            | `table-layout: fixed` + `text-truncate` |

## Архитектура

```
src/
  api/favoritApi.js       // API
  store/
    store.js              // configureStore
    searchSlice.js        // 2 thunk'а, requestId-гард
  components/
    SearchForm.jsx        // дебаунс, валидация, кнопка
    BrandList.jsx         // выбор бренда (этап 1)
    ResultsTable.jsx      // таблица предложений (этап 2)
    Loader.jsx            // индикатор загрузки
    ErrorBox.jsx          // inline-ошибки API/сети
    ErrorBoundary.jsx     // защита от падения рендера
  App.jsx                 // композиция этапов
```

### Компоненты-состояния (Loader / ErrorBox / ErrorBoundary)

Эти три компонента закрывают требования ТЗ «корректная обработка состояний загрузки и ошибок API». Они намеренно **тупые** (без Redux, без бизнес-логики) — их единственная ответственность — представить состояние, которое им передали. Это позволяет переиспользовать их в любом месте без привязки к `search`.

#### `Loader.jsx`

- **Роль:** единый индикатор загрузки для обоих этапов.
- **Вход:** `label?: string` (по умолчанию `"Загрузка..."`).
- **Поведение:**
  - Рендерит Bootstrap `spinner-border` + текст.
  - `label` — единственная кастомизация.
- **Использование:**
  - `App.jsx` — `<Loader label="Ищем производителей..." />` при `brandsLoading`;
  - `ResultsTable.jsx` — `<Loader label={`Загружаем аналоги ${selectedBrand}...`} />` при `analoguesLoading`.

#### `ErrorBox.jsx`

- **Роль:** показать **не-фатальную** ошибку от API/сети (например, `Invalid key client!`, `Request quota exceeded!`).
- **Вход:** `message?: string`.
- **Поведение:**
  - `if (!message) return null;` --> рендерит `alert alert-danger`.
  - `null` при пустом `message` — чтобы не рендерить пустой `div` в `App`.
  - Ошибка приходит **строкой** из `favoritApi.js` (`throw new Error(data.error)`), поэтому компонент не парсит структуру — UI не знает про контракт API.
- **Использование:** `App.jsx` — `<ErrorBox message={error} />` из `searchSlice.error`.
- **Чего не делает:** не ловит падения рендера (это `ErrorBoundary`), не показывает 404 на пустой `goods` (это «ничего не найдено» в `App`/`ResultsTable`).

#### `ErrorBoundary.jsx`

- **Роль:** последний рубеж — перехватить **падение рендера** (например, `undefined.toLocaleString()`), чтобы пользователь увидел сообщение, а не белый экран.
- **Вход:** `children`.
- **Поведение:**
  - `getDerivedStateFromError` --> `hasError: true`;
  - `componentDidCatch` --> `console.error`;
  - при `hasError` рендерит `alert alert-danger` + кнопку «Перезагрузить» (`window.location.reload`).
- **Почему класс, а не функция:** React **не даёт** функционального аналога `componentDidCatch`. Это единственный компонент в проекте, где класс обязателен.
- **Использование:** `index.js` — оборачивает `<App />` **внутри** `<Provider>` (чтобы при падении ошибка не «отравила» store и можно было перезагрузиться чисто).
- **Чего не делает:** не ловит ошибки в event handlers (они идут в `try/catch` внутри thunk'ов) и не ловит async-ошибки — для них `ErrorBox`.

### Разделение ответственности

| Ситуация                       | Кто отвечает                            | Почему                                  |
| ------------------------------ | --------------------------------------- | --------------------------------------- |
| `fetch` в процессе             | `Loader`                                | визуальный индикатор, без логики        |
| `fetch` вернул `{error}` / 4xx | `ErrorBox` (через `searchSlice.error`)  | не-фатально, можно продолжить работу    |
| `fetch` не нашёл товар         | пустое состояние в `App`/`ResultsTable` | это **не ошибка**, а валидный ответ API |
| Рендер упал                    | `ErrorBoundary`                         | фатально, нужен reload                  |

Такое разделение закрывает все четыре состояния («загрузка», «ошибка», «пусто», «успех») и не дублирует логику.
